# Core Engineering, Testing & Deployment Invariants

1. **Physical Immutability & Ephemeral Workspaces**:
   - **Kernel Read-Only Invariant**: `/share/aerial-config` and `/share/aerial` are mounted strictly **read-only (`:ro`)** into `eri`. Direct file writes or local git mutations targeting `/share/*` will fail with `EROFS: Read-only file system`.
   - **Ephemeral Scratch Workspaces**: Author all code, configuration, persona, skill, and repository updates across ANY repository (`aerial`, `aerial-config`, `mirrormere`, `aerial-sidecars`, etc.) in isolated scratch clones initialized via `scripts/aerial-pr.sh init [repo]`. Never use wrapper scripts, manual clones, or raw GitHub MCP PR tools (`create_pull_request`, `merge_pull_request`).

2. **Continuous Deployment, Execution Routing (`aerial-build.sh` vs. `aerial-pr.sh`) & Skill Triggers**:
   - **Scoped `self-improvement` Skill Activation**: Load `.agents/skills/discord/self-improvement/SKILL.md` when undertaking **any multi-PR or cross-repo rollout (≥2 PRs), Tier 1/2/3 features, bugfixes, or refactors, Girl Gang plan/diff reviews, Vanadis builds, database schema migrations, or CI/RoboRev failure remediation**. Single-PR Tier 0 (≤5 LOC config/doc tweaks) may execute directly following these invariants.
   - **On-Demand Language Engineering Skills (Progressive Disclosure)**: Before writing, reviewing, refactoring, or testing language-specific code (or authoring a Vanadis build plan targeting those languages), load the matching skill on demand so language rules stay out of non-coding turns:
     - **Go (`.go`, `go.mod`, Bazel `go_test`, `pgtest`, Restate SDK)**: Load `.agents/skills/discord/go-engineering/SKILL.md`.
     - **Rust (`.rs`, `Cargo.toml`, Tokio/Axum, ONNX `ort`, FFI/CUDA)**: Load `.agents/skills/discord/rust-engineering/SKILL.md`.
     - **Kotlin, Android & Wear OS (`.kt`, `.kts`, Jetpack Compose, Wear Compose M3, Tiles/Glance, NFC HCE, Keystore)**: Load `.agents/skills/discord/kotlin-wear-android/SKILL.md`.
   - **Default Execution Routing (Vanadis Build vs. Single-PR Submit)**:
     - **Vanadis vs. Docket Workflow Boundaries**: Vanadis (`aerial-build.sh`) is strictly reserved for active PR/chunk execution of multi-PR and cross-repo builds; Docket (`docket-mcp`) is strictly reserved for deferred backlog tracking, multi-stage epics, token-exhaustion parking, and mid-flight out-of-scope discoveries via DAG tools (`ready`, `list`, `search`, `show`, `create`, `update`, `comment`, `link`, `close`).
     - **Tier 1+ / Multi-PR / Cross-Repo / Sequential Rollouts (`scripts/aerial-build.sh enqueue <plan.json>` by Default)**: For Tier 1 bugfixes/features or whenever a task, migration, or Two-Step Feature Rule change requires **≥ 2 PRs** (across `mirrormere`, `aerial-sidecars`, `aerial`, and `aerial-config` or explicit `depends_on` DAG fan-out in one repo), **always propose and execute it as a Vanadis build** (`scripts/aerial-build.sh enqueue` with per-chunk `"repo"` fields after loading `.agents/skills/discord/self-improvement/references/vanadis-build-authoring.md`) to keep the primary channel daemon and root transcript featherweight. Multiple Vanadis builds execute concurrently in parallel—enqueue independent builds immediately (or use `append_chunk` for DAG additions) without waiting for an in-flight build to finish. Never propose or execute manual turn-by-turn *"kick off Step 1 PR now, wait for deploy, then run Step 2"* loops.
     - **Single-PR Tier 0 Changes (`scripts/aerial-pr.sh submit <scratch_dir> [commit_msg]`)**: When a Tier 0 tweak ships in a single PR in one repository:
       - **Zero-Bypass Verification**: Always run `./scripts/verify.sh --staged` (and targeted package tests) locally before submitting; never commit or push unverified changes.
       - **Mandatory PR Descriptions**: Provide `PR_DESCRIPTION.md` in the scratch root (or `--body-file`) using the Inverted Pyramid format with zero markdown tables and a sanitized single-line title.
   - **Amend Active Builds Immediately When Scope Changes**: Update pending chunks or add corrective chunks during the same turn, while allowing a safe executing chunk to continue. Place corrections before affected dependent work. Do not wait for the current chunk to finish before editing the build. Preserve completed and unaffected work; interrupt or cancel only when explicitly requested or when concrete risk cannot be addressed through subsequent chunks.
   - **Immediate Turn Termination**: Both `aerial-build.sh enqueue` and `aerial-pr.sh submit` arm automated event-driven progression and return `"turn_action": "end_turn"`. **The active turn MUST terminate immediately upon enqueue or PR submission**—never poll CI in foreground `sleep` loops or schedule PR follow-up reminders.
   - **Event-Driven CI Remediation**: Green CI merges and deploys automatically via `synapse`, Flux CD, and `git-sync`. If CI checks or `roborev` fail and wake `eri`, consult `.agents/skills/discord/self-improvement/SKILL.md` (Section 3) to proactively remediate the branch or record a verified technical override.

3. **Core Software Engineering & Hermetic Testing Invariants**:
   - **Production Database, Single-Service Table Ownership & Declarative Migrations**: Production runs on PostgreSQL 19 with `pgvector`. Every table in `schema.sql` is owned and queried by a single service; cross-service interaction happens over HTTP/MCP APIs rather than shared SQL queries. Define all schema modifications declaratively in `schema.sql`. Writing imperative DDL (`ALTER TABLE`, `DROP TABLE`) in application code or startup hooks is strictly prohibited and blocked by `scripts/verify.sh`. When modifying `schema.sql`, load and follow `.agents/skills/discord/self-improvement/references/atlas-migrations.md`.
   - **Pure Constructor Injection, Functional Core & Declarative Configuration**: Require explicit dependencies in constructors and factor business logic into pure, deterministic functions tested via fast unit tests. Define all non-secret service and feature configurations declaratively in dedicated YAML files in `aerial-config` (`services/**/*.yaml` or `config.yaml`). Never introduce ad-hoc environment variables for non-secret settings or feature flags; environment variables are strictly reserved for secrets and tokens injected via Infisical and External Secrets Operator into scoped per-service Kubernetes Secrets (with `shared-secrets` mounted at `/secrets` for harness redaction).
   - **Test Purity, Defense-in-Depth, Isomorphism & Zero Sleeps**:
     - Assert observable behavior using hand-derived literals or static fixtures—never internal constants, exact log wording, or values computed by the helper under test. Never assert on mock internal call counts; mock only external boundaries (never the database) with full intra-package parallelism, and keep test-only hooks out of production types.
     - Validate inputs across all layers (API entry, domain logic, environment guards).
     - **Isomorphism Rule**: Only unify functions, handlers, types, or test cases when they share the **exact same data contract and control-flow shape**—never merge heterogeneous behaviors behind mode-discriminator switches or one-hot boolean flags.
     - Arbitrary sleeps, live external CLI subprocesses, and unisolated host filesystem writes (to `/data` or `/share`) are strictly prohibited in unit tests.
